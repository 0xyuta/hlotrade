# HLO app (app/)

The browser app: trade Hyperliquid perps with the HLO builder fee, move USDC in and out, and claim and stake HLO. The design is spec §6 (`docs/superpowers/specs/2026-10-27-hlo-design.md`). Citations such as [T §n], [R §n] and [P4 §n] point to research notes that are not in this repository.

## 1. How it fits together

- **No server in the trading path.** The browser talks straight to `api.hyperliquid(-testnet).xyz` (HTTP and WebSocket) through `@nktkas/hyperliquid` 0.33.3. The only server code is `app/worker/` (a Cloudflare Worker: country block, `/api/register` through its R2 binding, security headers, the `www` redirect).
- **Two kinds of signer.**
  - The user's wallet (found with EIP-6963) signs only user-signed actions: approve the builder fee, approve an agent, and transfers. It signs through `hl/injected.ts` ("Fix A"), which calls `eth_signTypedData_v4` itself, because viem 2.57.12 rejects Hyperliquid's `:` primary types.
  - A local agent key signs orders, cancels and leverage changes, and Hyperliquid's referral actions (`setReferrer`, `registerReferrer`, `claimRewards`; `REFERRAL_SIGNER` in `hl/referralActions.ts` is the one switch to the main wallet if RF1 shows agents are refused). It can trade but never withdraw.
- **Agent keys: one per device.** Each device has its own named agent, so two devices never share a nonce stream and a phone can be cut off alone.
  - The computer's agent is named `hlo`. It is made by "Enable trading" (two wallet signatures the first time: the builder fee at 0.1%, then the agent). Running "Enable trading again (new key on this computer)" replaces it.
  - The phone's agent is named `hlo phone`. The main wallet approves it when you press "Approve phone and show pairing code" (one extra signature). Approving the same name again replaces the old phone key, so showing a new code cuts off the phone paired before.
  - The computer's agent is approved with `valid_until` 179 days ahead (`hl/agent.ts`, `AGENT_VALID_DAYS`), the phone's with 30 days (`PHONE_AGENT_VALID_DAYS`), so a forgotten phone's key stops working within a month; the computer can also cut it off at any time (below).
  - Keys live only in `localStorage` of the device that uses them: `hlo:agent:<network>:<master>` (computer) and `hlo:agent:<network>:<master>:hlo phone` (phone), plus `hlo:paired:<network>` on the phone. The computer's key never leaves the computer. The computer keeps `hlo:phone:<network>:<master>` = the phone agent's address and expiry, never its key, for the account menu.
- **Pairing a phone** never puts a key in a URL (Plan 4).
  - On the computer, Account → Pair phone first shows a code for the plain page `https://<host>/pair` (nothing secret). The phone opens that page, plain `/pair`, by scanning this code with its camera app or by typing the address. Then "Approve phone and show pairing code": the main wallet approves the phone's own agent `hlo phone` (one signature), and the modal shows the **pairing code**: the text `hlo pairing code <network> <68 hex>` (the key and a 4-hex checksum) as a QR, and the same 68 characters in 17 groups of 4 to type. It is not a link. It hides itself after a minute (Show again needs no new signature) and is dropped when the modal closes.
  - On the phone, `/pair` scans the pairing code inside the page (the browser's `BarcodeDetector`, else jsQR 1.4.0 loaded only then; iPhones currently use jsQR, since no iPhone browser has a QR-capable `BarcodeDetector` yet) or takes it typed. The checksum catches typos: a typo stays in the field to be corrected, while a typed code for the other network, or one that is not a valid key, is cleared from it. The phone asks Hyperliquid whose agent the key is (`userRole`), asks "Pair this phone with 0x…?" and shows the whole address under it (a short 4 + 4 form can be matched by a made-up address), and only then stores it. Leaving the page forgets an unconfirmed code.
  - Scan the pairing code from the pairing page, not the camera app: a camera app shows QR text with a "search the web" button, and searching would send the key to a search engine (checklist P2).
  - An old `/pair#…` link (Plan 3) no longer works. The page drops the fragment from the address bar unread, nothing is stored, and the page says "This pairing link is no longer used…". The old link can still sit in the phone's history; its key keeps trading until it expires (30 days after it was made) unless the computer cuts the phone off.
  - **The pairing code is visible on the computer's screen while it is shown**, for at most a minute at a time (and again each time "Show again" is pressed). While it is up, anyone who can see or photograph the screen, a screen share, or a browser extension that reads the page can copy the key. The typed groups are not select-all and the QR image cannot be dragged out of the dialog, but a deliberate copy, a screenshot or "Save image" still makes a copy that outlives the minute (clipboard history, cloud clipboard). Pair in private, and never copy the code: the phone types it.
  - Anyone who gets the pairing code can trade on the account, never withdraw, until the phone's key expires 30 days after pairing.
  - **Cut off paired phone** (account menu, computer only): the main wallet signs one `approveAgent` named `hlo phone` for a fresh throwaway address whose key is dropped at once and valid for 1 day (`CUTOFF_VALID_MS`). Hyperliquid replaces the named agent, so the paired phone's key stops working immediately. Pairing a new phone does the same.
  - **A lost answer may already have cut the old phone off.** If a re-pair or a cut-off signs the `approveAgent` and Hyperliquid's answer is lost (a network error, a timeout, a 5xx), Hyperliquid may have accepted it and the old phone is already cut off. The computer keeps its record of the phone, and for a cut-off the menu says so ("Cutting it off again is safe"). The fix is to re-pair, which gives a new working phone, or to cut off again, which is safe. A re-pair whose answer was lost shows no code.
  - A paired phone can only trade; Deposit, Withdraw, Claim, Stake, protocol buttons and profile edits say "Open HLO on the device with your wallet to do this." (`wallet/permissions.ts`).
- **Rewards** come from two places:
  - viem reads of the HyperEVM contracts;
  - the poster's public files (`docs/OPS.md` §10) under the network config's `rewardsBase`: `latest.json` (the checkpoint, the vault and the last pops), `checkpoints/<minute>.json`, and for a connected wallet its own `users/<xx>.json`.

  "Now" for every chain decision (the claim, the pool countdown) is the latest HyperEVM block's timestamp, not the wall clock. Rewards come from signed checkpoints: the poster publishes `latest.json` under `rewardsBase` (small: the checkpoint, the vault and the last pops; no wallet's numbers) and `checkpoints/<minute>.json`, and a connected wallet reads its own numbers and proof from `users/<xx>.json` (`xx` is the first byte of its address in lowercase hex; `docs/OPS.md` §10). Anyone settles a checkpoint on the `Checkpoints` contract, and `Mining.settleAndClaim` settles and claims in one transaction (`Mining.claim` when the chain already holds that checkpoint). The browser trusts nothing in a file by itself: `latest.json` and the user file are each used only if their EIP-712 signature recovers `Checkpoints.poster()` (this chain, this contract), they are not older than the chain's latest settled minute, and at the same minute their root is the chain's `rootOf` (`checkSigned` in `rewards/model.ts`; for `latest.json` the vault odds must also be the network's). The signature must also be one the contract accepts (v of 27 or 28, s at most n/2). The entries of a user file are not signed, so a wallet's entitlement is shown, and claimed, only if its proof verifies against the file's signed root (`rewards/proof.ts`, pinned by the shared `contracts/test/fixtures/merkle-vector.json`); the other numbers of the entry (points, refining) and the file's vault are display only. A nonzero entitlement whose proof does not verify, or that has none, makes that wallet's figures zero, Claim stays off and the card says "Your numbers in the rewards file don't match its signed tree." A 404 for the user file (nothing written yet for that part of the address space) means zero for the wallet, not an error; any other failure shows "The reward files could not be read (…)". A file that fails is ignored, the card says why, and Claim stays off. A file whose `refBlock` is not yet below the chain head is not a bad file; settling it simply waits. If HyperEVM does not answer, only the Rewards screen pauses; if only the Staking or Buyback reads fail, only those cards say so. The data reloads every 30 s while the tab is visible. The file read has a 10 s timeout. After a claim goes through, the claimed amount is held until a chain read shows `claimed` at or above it (at most 10 minutes), so a lagging node cannot make it claimable again. Mining pays claims from one hourly allowance shared by everyone (`claimAvailable()`, read with the chain): a claim larger than it is paid in part, so "Claimable now" stays the full amount, "You receive 90%" counts only what the allowance lets through (`claimNow`), and the card adds "Claims share an hourly allowance. You can claim X HLO now; the rest stays claimable." The hold is the `claimedTotal` of the `Claimed` log in the claim's receipt (what the contract really left in `claimed[user]`; a claim paid less than expected because the allowance moved holds that), or `claimed + min(rest, allowance)` (`ClaimPlan.expectClaimed`) when the receipt cannot be read; never the whole entitlement. While a hold is active the held difference is also taken off the local allowance, so Claim does not offer it again. A claim of less than 0.01 HLO counts as blocked (`MIN_CLAIM_NOW`). With the allowance empty Claim is off and says "Claims are at their hourly limit. Try again in a few minutes." (the text a `ClaimLimitReached` revert gives too).

  **Which file claims** (`claimPlan` in `rewards/model.ts`). The claim uses the user file's own checkpoint and its proof, and the chain decides the call:
  - the file is newer than the chain's latest settled minute, or nothing is settled: **Settle & claim**, with the file's own signed fields;
  - the file is at the chain's latest settled minute with the chain's root: **Claim**;
  - the file is older than the chain's latest settled minute: the app reads `rootOf(file.throughMinute)` (only in this state, and only after the signature check, so an ordinary poll costs no extra call). If it equals the file's root, that minute is still settled and not cancelled, `Mining` pays against any such minute, and the file still claims with **Claim** and no "updating" text (a wallet that has already claimed past the file's entitlement gets no claim). If it reads zero (never settled, or cancelled) or another root, the card says **"Rewards are updating…"** and offers no claim until a newer file lands. If that read fails, the card shows the same text until the next poll.

  The user files are written on rounds (every checkpoint under 2,000 wallets with an entry, every 5th minute under 20,000, every 15th above; `docs/OPS.md` §10), so a file can be older than `latest.json`. Anyone settling a minute that has no file, with the poster gone, leaves wallets on "Rewards are updating…" until a poster runs again (a known limit above 2,000 wallets, `docs/OPS.md` §2).

  **Fetch modes.** The user file is fetched with `cache: "no-cache"`: the browser asks the store whether it changed, an unchanged file costs a 304 with no body, and a changed one is never served from the cache unchecked. `no-store` would download about 230 KB (gzipped, at 100,000 wallets) on every 30 s poll on a phone. `latest.json` stays `no-store` (small, and it changes every minute).

  **The Vault card's dash.** A connected wallet with no points shows `0.00`, never a dash; not connected shows dashes. One exception: while `latest.json`'s `vault.lastPopMinute` is newer than the wallet's file (the vault popped after the file was written; above 2,000 wallets a file can lag the checkpoint), the file's points are the pre-pop ones and the share could exceed the vault, so "Your points since the last pop" and "Your share if it popped now" show a dash until the next file. "In the vault" and the last pop still show.
- **Referrals are Hyperliquid's own** (Plan 10, spec `docs/superpowers/specs/2026-10-30-hlo-referrals-tokenomics-design.md`); HLO has no referral contract.
  - The default code: a `?ref=CODE` link (a valid code only) is kept in `localStorage` `hlo.ref.<network>` and wins over the config's `referralCode`. While Enable trading is offered the app reads `referral` once; when the account has no referrer, the text under the Enable button names the code. Enable trading sends `setReferrer` with exactly that code (`enable(shownCode)` in `hl/TradingProvider.tsx`), signed by the new agent, after `referral` reads again with no referrer. No text shown means no code sent: the trading status unknown or still loading, the `referral` read pending or failed, and "Sign once to enable trading again" all set nothing, and a `?ref=` kept later in another tab is not used until a new read shows it. A refusal is logged to the console (no key in it), never blocks trading and is not retried.
  - Referral USDC is Hyperliquid's: it is paid to the account that owns the code (for default sign-ups, the owner of the config's `referralCode`), claimed with `claimRewards`, and never passes through the Splitter or the buyback.
  - The Referrals tab (`ui/referrals/`, rules in `hl/referral.ts`): the referrer (or a field and Use code), the account's own code (Create code after $10,000 traded; then the share link `https://<host>/?ref=CODE`, only for a code of letters and digits, which is all the `?ref=` capture keeps; another code is shown with a short note; the count and the referred accounts), and the USDC rewards with Claim. Without a live trading key it says "Checking your trading key…" while the status loads, then "Enable trading first" with its own Enable trading button (the same Enable text rule). A paired phone sees it but cannot act.
- **Mine mode** was removed on 2026-11-06 (git history has it). A leftover `localStorage` `hlo:mode` is ignored; claims and the vault are on Rewards.
- **`?coin=` links.** `hlotrade.xyz/?coin=HYPE` opens Trade on that market, on a phone too (not Markets). Only a plain market name is read (`hl/coinLink.ts`); it is not stored, and a name not listed falls back to the stored market. The "Trade on HLO" button on chart.hlotrade.xyz uses it.
- **The Explore tab** (`ui/explore/`, under More on a phone): live status (on time or how many minutes late, the last counted minute, what is on chain, a warning when claims are paused), the last 30 minutes (Pending, Counted, On chain, with fees, wallets and a pop mark), the connected wallet's last 30 trades through HLO (the points each earns, 1 per $1 of HLO fee, and Pending, Counted, Not counted with the reason) and the recent pops. Rules in `rewards/explore.ts`. The trades come from Hyperliquid in the browser and are compared with `checkpoints/<m>.json` (six files at a time, kept in memory; a published minute never changes). It writes nothing. The poster's signature covers the root, not the fee table, so the page is for reading only and decides no claim; the verifier checks the same tables against Hyperliquid. The registration date is not public, so a trade before it shows as Not counted with that reason in the text. Other wallets appear only as totals.
- **The Bots tab** (`ui/bots/`, under More on a phone, public link `/bots`): how to mine with your own bot. Register the wallet (Enable trading, or `approveBuilderFee` and `POST /api/register`), make an API wallet on Hyperliquid's API page, send every order with the builder field. The sample `public/bots/hlo-bot.mjs` buys a fixed amount on a schedule up to `MAX_USD`, reading the position so a restart keeps the limit, and sends nothing without `LIVE=1`. HLO holds no key and runs nothing. The page states the rules: no trading between your own wallets or only for volume (Hyperliquid's Terms §3.1.4), rate limits (§3.1.8), losses are possible.
- **The Tokenomics tab** (`ui/tokenomics/`): supply, mining, the vault, claiming and fees, with numbers from `rewards/constants.ts` (pinned to calc and the contract sources by `test/tokenomics.test.ts`) and the network's odds (`POP_ODDS`), plus live figures from the Rewards reads (dashes when not deployed).
- **Swap** (`ui/swap/`, lazy, a dialog). Mainnet only. Buy HLO in the top bar, or Swap on Rewards, opens the card over the current page. `/swap` opens Rewards with the card up; closing it leaves Rewards. The market is the deployment's Uniswap V2 pair (Buyback's factory `0x89e5DB8B5aA49aA85AC63f691524311AEB649eba`). The app swaps through Uniswap V2 Router02 `0x1f7d7550B1b028f7571E69A784071F0205FD2EfA`, whose `factory()` is that factory, so the path `[pay, receive]` is this pair. There is no HLO router, and testnet is not offered (its pair is not this market). The quote is the pair's live reserves through the v2 formula at 0.30% (`swap/quote.ts`); nothing on screen is a fixed price, and the pool's reserves are not shown. HLO uses the halo mark and USDC uses Hyperliquid's coin icon. Balances are the connected wallet's HLO and USDC. Slippage starts at 0.5% and can be set from 0.01% to 5%. The button approves the router for the exact amount when the allowance is short, then calls `swapExactTokensForTokens` with `amountOutMin` equal to the minimum already on screen. Right before that, the app reads the pair again: if the fresh quote is under that minimum, nothing is sent and the card asks the user to look again. The deadline is 20 minutes after the fresh block timestamp. A paired phone can read the quote and cannot send. Gas is a little HYPE on HyperEVM. The connected wallet is the same one as the rest of the app.
- **Deposits and withdrawals:**
  - HyperCore (spot↔perps for standard accounts);
  - HyperEVM (CoreDepositWallet `deposit(amount, 0)`, `sendAsset` back). Like the CCTP deposits, an existing allowance that covers the amount is reused. After a timed-out deposit, a second press skips the approval only if the approval landed and the deposit did not; if the deposit landed, it approves and deposits again (to the user's own account), so check the balance first;
  - Arbitrum and Ethereum through Circle CCTP v2 with the CctpForwarder hook (`sendToEvmWithData` back).
  - Solana through Circle CCTP v2 (Plan 4), when the config has `solanaEnabled: true`. Deposit: a Wallet Standard wallet (Phantom, Solflare, Backpack; not Phantom's embedded social-login wallets) signs a hand-built `deposit_for_burn_with_hook` with the same CctpForwarder hook as Arbitrum and Ethereum; a fresh event account co-signs, and the wallet pays about 0.004 SOL (fee plus the event account's rent, which the app does not reclaim). With `solana:signTransaction` the app records the transfer under its signature and event account before broadcasting it once; a broadcast with no answer is never repeated, and Iris or the signature status settles it. With the `solana:signAndSendTransaction` fallback (the wallet broadcasts) the app records the transfer by its event account before the wallet is asked, removes that record if the wallet says nothing was sent, and adds the signature when one comes back. Withdraw: `sendToEvmWithData` to domain 5 with `addressEncoding: "base58"`, the connected Solana wallet's USDC account as recipient, and Circle's createATA `data`; minimum 1.50 USDC (0.50 fee cap + 1). A Solana-only user still needs an EVM wallet: the Hyperliquid account is an EVM address. All Solana code loads only when the Solana route (or a Solana record's poll) needs it.
  - **Solana deposits are never re-sent.** The app signs and sends once. If the broadcast gets no answer, the row says "unconfirmed: watching the Solana transaction" and settles from the chain (the event account, which only exists if the transaction landed, and the signature status) and from Iris. A transaction that never landed ends as "not sent: … expired" after the blockhash window plus a 15 minute grace, with nothing moved; "expired" is said only once the event account reads as absent, never on an RPC read that did not answer. Nothing offers a retry.
  - **"not sent" rows.** A Solana deposit row whose note starts "not sent" (failed, expired, or refused by the node before sending) reads "not sent" instead of "pending…". A failed one is final at once; an expired or refused one is still watched for an hour (landing on chain would clear it), then it is final. A final row is no longer polled and gives way to a new transfer like a finished one, so it never counts toward the 20 records.
  - **Dismiss on Solana rows.** No Solana row offers Dismiss while a transfer is being signed or sent (the deposit's record is written before its broadcast). An unconfirmed Solana deposit offers Dismiss only after an hour: the chain decides it within minutes, and dismissing ends the watch.
  - **A buggy Solana wallet could still cause a second deposit.** Only a typed 4001 rejection reads as "nothing sent". A wallet that broadcasts the transaction and then reports a 4001 rejection would read as "nothing sent", and the user would deposit again. The cost is a second deposit to the user's own account, never a loss (`isUserRejection` in `wallet/solana.ts`).

  Robinhood Chain shows as "coming soon". Bridge2 is not used.
- **Pending transfers** live in `localStorage` (`hlo:pending:<network>:<user>`, 20 records). Only one transfer can be signed or sent at a time on the page (a lock), however the modal is navigated. The lock has no automatic release: after 60 s of waiting the modal says to check the wallet or reload the page. A held (unconfirmed) transfer also blocks any new transfer ("Resolve the unconfirmed transfer above first") until it is retried or dismissed. If Hyperliquid's answer to a user-signed transfer is not confirmed (network failure, timeout, an HTTP 5xx or 408, or a 2xx whose body is not JSON with a `status` field), the app does not sign again. Any other 4xx, or a `status: "err"` answer, is a real refusal. The record says "unconfirmed: check your balance before sending again" and offers "Retry (same request)", which re-posts the same signed body (same nonce, which Hyperliquid should dedupe). That signed body lives **only in page memory**, never in storage (`routes/unconfirmed.ts`). After a reload the record stays, but the Retry button and the lock are gone, so a new transfer is possible again: the user must check the balance before sending again. "Dismiss" removes a stuck record from the list; it cancels nothing on chain.
  - **Dismissing an unconfirmed record (Solana or EVM) stops its poll and frees its pending room, but the deposit can still arrive.** The app no longer watches it, so nothing will mark it done. **Check your balance before depositing again.**
- **Withdrawal "done" marks are a balance watch.** A withdrawal record is marked done when the destination balance rises by its `minArrive` over its baseline, and a second withdrawal to the same balance starts from the first one's `baseline + minArrive`. Two display-only edge cases remain (they never move money, and never block a new transfer):
  - If an earlier withdrawal arrives with more than its `minArrive` (its fee came in under the cap) and the excess is larger than the next withdrawal's `minArrive`, one arrival can mark both done.
  - If the user dismisses a withdrawal that is really still on its way and then starts another to the same chain, the new one starts from the plain balance, so the first one's arrival can mark it done early.

  In both cases the record says "done" too early; the balance itself is right. Check the balance on the destination chain when two withdrawals to the same chain overlap.
- **Country blocking:** `app/worker/index.ts` returns 451 (from Cloudflare's `request.cf` country and region) for the countries and regions in `app/src/geo/blocked.ts` (the US and its territories Puerto Rico, Guam, US Virgin Islands, American Samoa, Northern Mariana Islands and the Minor Outlying Islands; Cuba, Iran, Myanmar, North Korea, Syria; Ontario, Crimea, Sevastopol, Donetsk, Luhansk).
  - No country at all (local dev, unknown IP) passes: fail-open.
  - It applies to every request the Worker sees, `/api/register` included. Hashed `/assets/*` files skip the Worker.
  - Tor (`T1`) and unknown (`XX`) pass.
  - A country that has blocked regions (CA, UA) arriving **without** a region is blocked: fail-closed, because we cannot tell Ontario from the rest of Canada.
- **Chart attribution:** the chart's built-in TradingView logo is turned off (so the CSP needs no inline style). Attribution is a visible "Charts by TradingView" link under the chart and the notice text with the link in the footer, as the `lightweight-charts` NOTICE allows. Keep both when changing the layout.

## 2. Run it

```bash
npm install                 # at the repo root (workspaces: calc, ops, app)
npm run dev -w app          # http://localhost:5173, dev.json (Hyperliquid testnet, read-only: no builder, no contracts)
npm run dev:testnet -w app  # testnet.json
npm test -w app             # unit tests (vitest)
npm run typecheck -w app
npm run build -w app        # mainnet.json
npm run build:testnet -w app
npm run dev:worker -w app   # builds testnet, then runs the Worker with the built app (wrangler dev), http://localhost:8787
```

`npm run dev` is Vite only: it has no Worker, so there is no country block and no `/api/register`. To run the Worker locally use `dev:worker`. It uses the `hlo-testnet` bucket binding in a local simulation, not the real bucket; add `--remote` (`npm run build:testnet -w app && npm exec -w app -- wrangler dev --env testnet --remote`) to run against Cloudflare's network and the real bucket, which is how H4 reads the country.

**Node.** `app/package.json` (and the root `package.json`) say `engines.node >=22.12`: `@wallet-standard/app` needs Node 22, and `@nktkas/hyperliquid` needs **22.12 or newer** (`app/test/engines.test.ts` checks the floor against both). The range is open on purpose (local development runs a newer Node, and `22.x` would warn on every install). The deploy scripts run `vite build` on the owner's Mac, so the Node there must satisfy `engines`.

**Code split (Plan 4).** The entry chunk holds React, the config and the shells; the trading app, the rewards screen, the transfer modal, the pair modal (with `qrcode`), the chart (with `lightweight-charts`), the phone's `/pair` page, jsQR and all Solana code are separate chunks. Every `vite build` checks this (`app/chunkCheck.ts`) and fails if a listed module is reachable from a chunk's static imports; the phone's `/pair` page has an allow-list (its own `ui/pair`, the shell, the config, the formatter and the pairing modules), so a new `src/` directory is the App's by default. A lazy part that fails to load (the rewards screen, the chart, the transfer and pair dialogs, the Solana form) shows "Try again" in its own place, never the page-wide fallback (section 4: after a redeploy). ## 3. Config

There is one JSON per network in `app/src/config/`: `mainnet.json` for `npm run build`, `testnet.json` for `npm run build:testnet` (and `dev:testnet`), and `dev.json` for `npm run dev`. Only the build's own file is bundled.

| Key | Required | Meaning |
|---|---|---|
| `network` | yes | `"mainnet"` or `"testnet"`; must match the build |
| `hyperEvmRpc`, `arbitrumRpc`, `ethereumRpc` | yes | https RPC URLs (http on localhost allowed in dev.json). They also go into the CSP |
| `withdrawEnabled` | yes (in any filled file) | `true` or `false`. **What the Worker does** (`app/worker/index.ts`, in this order): the country block (451, every Worker route), `POST /api/register` (405 for another method, 404 for another `/api/*` path), the `www` redirect (301 to the bare domain with the path and query), then the built app (`ASSETS`, with `not_found_handling: none`). The Worker serves `index.html` for unknown pages itself (a 404 from `ASSETS` for GET or HEAD is answered with `/`), so `/pair` and any app route load and the country block covers them; a missing `/assets/*` file is a plain 404 (it never runs the Worker, and must not serve the app). `run_worker_first` is `["/*", "!/assets/*"]`: only the hashed `/assets/*` build files skip the Worker; they are free and get `Cache-Control: public, max-age=31536000, immutable` plus the security headers from `app/public/_headers` (Vite copies it into `dist/`; H3 checks that it applies). Every response the Worker returns carries the same security headers (`app/worker/headers.ts`): `frame-ancestors 'none'` (also `X-Frame-Options: DENY`), `X-Content-Type-Options: nosniff`, `Referrer-Policy: no-referrer`, `Permissions-Policy` with `camera=(self)` for the pairing scanner, `Cross-Origin-Opener-Policy: same-origin-allow-popups`, and HSTS. The Worker's free tier is 100,000 requests a day.

**Registration** (`app/worker/register.ts`): the Worker writes an empty index entry `registry-log/<chainId>/<registeredAt, 10 digits>-<user>.json` first (the poster and the verifier list the index to find new wallets), then `registry/<chainId>/<user>.json` through its `REGISTRY` binding, with `If-None-Match: *` so a record is written once; a failed index write answers 502 and writes no record. The app holds no R2 keys. The network comes from `HLO_NETWORK` (a plain var in `wrangler.jsonc`), never from the request. `registeredAt` is the Worker's clock in unix seconds. A repeat costs one `head` and no Hyperliquid call. The answers: 200 `{registered: true}`, 400 bad body, 403 below the builder fee, 502 Hyperliquid or bucket failure, 503 when `HLO_NETWORK` or the network's builder is missing.

## 7. When something goes wrong

- **"Your trading key is no longer approved…"**: the agent expired or was replaced. On a computer, sign once ("Enable trading"). On a paired phone it says to pair again from the computer: the phone's key cannot be renewed on the phone.
- **"A transfer may not have gone through"** (unconfirmed): check the balance first. If it did not arrive, "Retry (same request)" re-sends the same signed request (it works only until the page is reloaded). After a reload, or if the balance shows the transfer happened, use "Dismiss" to clear the row. Never start the same transfer again before checking.
- **"Rewards are paused"**: HyperEVM did not answer. Trading is unaffected.
- **"A reward file did not match the chain"**: the file is stale or tampered. The app ignores it. Tell the poster's operator (`docs/OPS.md` §5).
- **A CSP violation**: a host is missing from the config (section 3).
- **A 451 page for a user who should be let in**: the country block failed closed (a country with blocked regions and no region header). Check the region codes in H4.
- **"This pairing link is no longer used"** on a phone: the phone opened an old `/pair#…` link. Nothing was stored. Pair from the computer (Account → Pair phone) and scan from the pairing page. If an old link might have been seen by someone else, press "Cut off paired phone…" on the computer first.
- **"That is not an HLO pairing code"**: the phone scanned the link code or another QR. Scan the second code, shown after approving.
- **"The answer from Hyperliquid did not arrive, so the phone may already be cut off"** (Cut off paired phone): the approval may have gone through. Cutting off again is safe.
- **Pair phone shows an error after you approved in the wallet, and no code** (a network error or no answer from Hyperliquid): the approval may have gone through, so the phone paired before may already be cut off. Press "Approve phone and show pairing code" again (one more signature) to pair a phone.
- **A Solana row says "unconfirmed: watching the Solana transaction"**: the deposit was signed and sent but Solana's answer was lost. Do not deposit again; check the wallet's activity. The row settles from Iris or the chain; "not sent: … expired" means it never landed and nothing moved. "Dismiss" (offered after an hour) stops the watching but cannot stop the deposit: check your balance before depositing again.
- **A Solana row reads "not sent"**: Solana refused, failed or expired the transaction; nothing moved (a failed one cost only the network fee). It stops counting toward the 20 records once it is final: a failed one at once, an expired or refused one after an hour. Dismiss it when you like.
- **"This browser cannot create the Solana transaction"**: the browser has no WebCrypto Ed25519 (an old Chrome or a Chromium fork). Nothing was sent. Update it, or use Chrome, Safari 17+ or Firefox 129+.
- **A Solana deposit says "The wallet changed the transaction"**: nothing was sent. See SOL2.
